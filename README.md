# Cohort Data Builder

Search the variables of CLS longitudinal studies, pick the ones you need, and
download R or Python code that reads them from your own copy of the data and
merges them into one file.

Datasets: **BCS70** (1970 British Cohort Study) and **Next Steps**.

This site and repository contain **no study data**, only the published data
dictionaries: variable names, labels, value labels and missing-value codes.
You supply the data files from the UK Data Service; the downloaded scripts run
on your own machine.

## Using it

1. Pick a dataset and search by variable name or label. Filter by sweep (click
   the axis), by measurement level, or by file.
2. Add variables with **＋**. The **Selection** tab shows the output columns;
   rename any that clash.
3. Choose R, Python or both, and whether missing-value codes become NA, then
   download.

The download is a small project:

```
<dataset>-merge-<date>/
  README.md          which data files are needed, and how to run it
  codebook.csv       every output column: source, label, value labels, missing codes
  data/              put the data files here (any format, subfolders fine)
  R/load_data.R      finds each file by name and picks the read call from its extension
  R/merge.R          your selection and the merge: run this
  python/load_data.py
  python/merge.py
```

It writes `output/merged.csv`, one row per person joined on the study's
identifier. A file with several rows per person (household grids, histories)
is written to its own `output/<file>_long.csv` instead of being joined.

`.tab` needs nothing beyond base R or pandas; `.dta`/`.sav` need R's `haven`,
and `.sav` needs Python's `pyreadstat`.

## Repository layout

```
datasets/<key>/      the metadata for each dataset — see docs/metadata-spec.md
  raw/               the deposit's RTF data dictionaries: on your machine only
                     (git-ignored); raw/README.md says where to get them
  dictionaries/      parsed from raw/, one folder per wave (age), committed
schema/topics.yaml   the topic schema variables are tagged with
enrich/              the tagging pipeline (python -m enrich)
templates/           the R, Python and README templates the download is made from
site/                the static site (no build step, no framework)
  js/                one module per concern: boot, search, basket, codegen, zip
  data/              generated by build.py, not committed
build.py             validates datasets/ and writes site/data/
tools/               parse_dictionaries.py (raw RTFs to dictionaries) and the
                     RTF converter it uses
tests/
```

## Running it locally

```
python3 build.py                      # validate and build site/data/
python3 -m http.server -d site 8000   # then open http://localhost:8000
```

`build.py` is standard library only. `python3 build.py --check` validates
without writing.

## Tagging variables by topic

Every variable can carry topic tags, such as *Smoking* or *Household
composition*, each with a confidence. The site uses them for a **Topic**
filter (with a confidence threshold), chips on each result, and a confidence
breakdown on each variable; the download's `codebook.csv` lists them.

The tags are assigned by an LLM through [Ollama](https://ollama.com):

```
uv sync                                  # once
uv run python -m enrich next_steps       # tag one dataset
uv run python -m enrich --all            # or every dataset
python3 build.py                         # then show them on the site
```

It shows progress as it goes (variables tagged and left, failures, speed,
time remaining) and can be stopped with Ctrl-C at any point: the next run
carries on where it stopped. Useful options (`--help` lists them all):

| Option | Default | |
|---|---|---|
| `--model` | `gpt-oss:120b-cloud` | any Ollama model with structured output |
| `--batch-size` | 20 | variables per request |
| `--workers` | 4 | requests in flight at once |
| `--files` | all | only these data files |
| `--limit` | all | at most this many variables, to try things out |
| `--retag` | off | redo variables that already have current tags |
| `--dry-run` | off | print the first prompt and stop |
| `--ollama-url` | `http://localhost:11434` | |

A `-cloud` model runs on Ollama's servers, so variable names, labels and
value labels leave your machine; no study data is ever involved. Use a local
model to keep everything on the machine.

**The topics are defined in [`schema/topics.yaml`](schema/topics.yaml)**:
15 domains and around 100 topics, based on the CLOSER Discovery controlled
vocabulary (the two-level topic scheme CLOSER uses for UK longitudinal
studies, built from MeSH and ELSST), with cross-references to the CESSDA
Topic Classification. Edit it freely: the model reads each topic's
description, and any change marks existing tags as stale so the next run
redoes them.

How it works: each batch goes to the model with the schema's guidance,
topics and the format instructions of a LangChain `PydanticOutputParser`.
Ollama is held to the same Pydantic model's JSON schema, whose topic field is
an enum of the schema's ids, so the model cannot invent a topic; the parser
checks every reply, including that each confidence is between 0 and 1. Failed
batches are retried, and any variable the model skipped is retried on its
own. The identifier column is tagged by rule, without the model.

Tags are stored in `datasets/<key>/tags/`: `tags.jsonl` (one line per
variable, with the model and schema that made it) and `schema.json` (the
schema snapshot the site reads, so `build.py` needs no YAML parser).

## Updating the dictionaries

The parsed dictionaries are committed; the RTFs they come from are not. To
regenerate them, put the RTFs in place (each `datasets/<key>/raw/README.md`
says where they come from), then:

```
python3 tools/parse_dictionaries.py    # every dataset with RTFs in raw/
git add datasets/*/dictionaries
```

## Tests

```
uv sync --extra test
python3 build.py
uv run python -m unittest discover -s tests
```

`test_build.py` covers the metadata rules, the RTF converter and the parse.
`test_enrich.py` covers the tagging pipeline against a stub model, so it
needs `uv sync` but not Ollama.
`test_generated_scripts.py` generates a real download, runs its R and its
Python on fabricated `.tab`, `.dta` and `.sav` files, and checks both give
the same, correct output. It needs node, and skips the parts whose tools
(Rscript with haven, pandas, pyreadstat) are not installed.

## Deploying

`.github/workflows/pages.yml` builds `site/data/` and publishes `site/` to
GitHub Pages on every push to `main`. Set **Settings → Pages → Source** to
**GitHub Actions**.
